# HB+ App

HB+ is a cross-platform Expo/React Native application with Supabase authentication. It provides email/password and Google sign-in and exposes a dashboard only to users whose confirmed account uses an approved organization domain.

The default approved domain is `hbplus.fit`.

## Technology

- Expo SDK 58
- React and React Native
- Supabase Auth
- Supabase PostgreSQL `profiles` table
- `expo-auth-session` and `expo-web-browser`
- `@react-native-async-storage/async-storage` for native session persistence

## Project structure

```text
App.js                       Application root and auth gate
index.js                     Expo root component registration
src/config/domain.js         Allowed-domain configuration and email validation
src/config/supabase.js       Supabase client and session persistence
src/context/AuthContext.js   Authentication methods and session handling
src/screens/AuthScreen.js    Login and registration UI
src/screens/DashboardScreen.js
                             Authenticated dashboard
```

## Prerequisites

Install the following:

- Node.js 20 or newer
- npm
- Git
- A Supabase project
- Google OAuth credentials, if Google sign-in is needed
- Expo Go or a configured iOS/Android development build

Expo Go can run the JavaScript-only setup. Native builds require a development build only when native modules or custom OAuth configuration are added.

## Setup

### 1. Install dependencies

From the repository root:

```bash
npm install
```

### 2. Configure environment variables

Create or update `.env` in the repository root:

```dotenv
EXPO_PUBLIC_ALLOWED_DOMAIN=hbplus.fit
EXPO_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT_ID.supabase.co
EXPO_PUBLIC_SUPABASE_ANON_KEY=YOUR_SUPABASE_PUBLISHABLE_OR_ANON_KEY
```

| Variable | Required | Purpose |
| --- | --- | --- |
| `EXPO_PUBLIC_ALLOWED_DOMAIN` | No | Domain after `@` that may authenticate. It defaults to `hbplus.fit` if omitted. Do not include `@`. |
| `EXPO_PUBLIC_SUPABASE_URL` | Yes | The Supabase project URL. |
| `EXPO_PUBLIC_SUPABASE_ANON_KEY` | Yes | A Supabase public/anon or publishable key. It is safe to bundle in a client app; it is not a service-role key. |

Never put `SUPABASE_SERVICE_ROLE_KEY`, database passwords, or other server secrets in `EXPO_PUBLIC_*` variables. Expo bundles public variables into the application.

The existing `.env` contains project-specific values. Replace them with your own project values before using a separate environment. Restart Expo after changing environment variables.

### 3. Configure Supabase Auth

In the Supabase dashboard:

1. Open **Authentication > Providers**.
2. Enable **Email**.
3. Enable **Confirm email** if email verification should be required.
   - The app always rejects users when `email_confirmed_at` is missing.
   - Supabase sign-up sends the verification link even if confirmation is already enabled.
4. Enable **Google** and add the Google OAuth client credentials.
5. Open **Authentication > URL Configuration**.
6. Add the application redirect URLs used by the app.

For web, the redirect URL is the current site origin, such as:

```text
http://localhost:8081
https://your-production-domain.example
```

For native development, run the app and use the exact redirect URI generated by `makeRedirectUri()`. Add that URI, or the intended production deep-link URI, to the Supabase **Redirect URLs** allow list and to the OAuth provider configuration.

The app's web OAuth redirect uses `window.location.origin`. The native OAuth redirect is created with Expo's `makeRedirectUri()`.

### 4. Configure the Supabase database

The application reads the user's role from this table:

```sql
create table if not exists public.profiles (
  id uuid primary key references auth.users(id) on delete cascade,
  role text not null default 'user'
);

alter table public.profiles enable row level security;

create policy "Users read their own profile"
on public.profiles
for select
to authenticated
using ((select auth.uid()) = id);
```

The app expects a `profiles.role` value. If no profile row is found, it defaults to `user`.

A trigger should also create a profile after a user is created and reject users outside the approved domain. The following is a recommended base implementation:

```sql
create or replace function public.handle_new_user()
returns trigger
language plpgsql
security definer set search_path = public
as $$
begin
  if new.email is null
     or lower(btrim(new.email)) not like '%@hbplus.fit' then
    raise exception 'Access restricted. Please login using your official domain email.';
  end if;

  insert into public.profiles (id, role)
  values (new.id, 'user')
  on conflict (id) do nothing;

  return new;
end;
$$;

drop trigger if exists on_auth_user_created on auth.users;

create trigger on_auth_user_created
after insert on auth.users
for each row execute function public.handle_new_user();
```

If you change `EXPO_PUBLIC_ALLOWED_DOMAIN`, update the `%@...` check in this trigger too. The database trigger and app environment must use the same domain.

This trigger is server-side protection. App-side validation improves the user experience but does not replace database or Row Level Security (RLS) enforcement.

### 5. Start the app

```bash
npx expo start
```

Useful launch commands:

```bash
npx expo start --web
npx expo start --android
npx expo start --ios
```

The web command requires no native build. Android/iOS require Expo Go or a compatible Expo development build. Press `w`, `a`, or `i` in the Expo terminal menu to open web, Android, or iOS targets.

## Authentication flow

### Application initialization

1. `App.js` wraps the app in `AuthProvider`.
2. `AuthProvider` subscribes to Supabase `onAuthStateChange`.
3. Session restore and the initial auth event set the `initializing` state.
4. `handleSession` validates the session user.
5. A valid, confirmed, allowed-domain user is stored in React context and opens the dashboard.
6. Otherwise, the auth screen is shown.

### Email registration

1. The user enters a name, work email, password, and password confirmation.
2. The UI rejects names shorter than two characters, passwords shorter than six characters, mismatched confirmations, and disallowed domains.
3. `registerWithEmail` performs one more domain check.
4. Supabase `signUp` creates the Auth user and sends a verification email when email confirmation is enabled.
5. The app stores the user's name in Supabase `user_metadata.full_name` and directs confirmation back to the app redirect URL.
6. The app explicitly signs out if Supabase unexpectedly returns a session before verification.
7. The user must open the verification link and then log in.

Supabase may report an existing account as a user with no identities. The app recognizes this result and presents an existing-account error rather than falsely confirming registration.

### Email login

1. The UI validates the allowed domain.
2. `loginWithEmail` performs another domain check.
3. Supabase authenticates with `signInWithPassword`.
4. Supabase emits an auth-state event containing the session.
5. `handleSession` verifies the user email, confirmation state, and domain.
6. The app loads `profiles.role` and exposes the user to the dashboard.

Incorrect credentials, unconfirmed email, rate limits, network failures, and weak passwords are converted to friendly messages.

### Google login

**Web**

1. The app calls Supabase `signInWithOAuth` with the Google provider.
2. The Supabase/Google flow redirects the browser to Google.
3. The `hd=hbplus.fit` parameter is sent as a hosted-domain hint and `prompt=select_account` requests account selection.
4. Google redirects back to `window.location.origin`.
5. Supabase detects the session in the URL and emits an auth-state event.
6. `handleSession` independently verifies that the returned email is confirmed and belongs to the allowed domain.

**Native**

1. The app calls Supabase OAuth with `skipBrowserRedirect: true`.
2. Expo WebBrowser opens the Google/Supabase authorization URL.
3. The browser result returns to the app redirect URI.
4. The app reads OAuth tokens from the callback URL.
5. Supabase `setSession` creates the local authenticated session.
6. The normal auth-state listener performs the same domain and confirmation checks.

OAuth cancellation or dismissal leaves the app on the auth screen without an error.

### Session persistence and logout

- Native platforms persist sessions with AsyncStorage.
- Web uses browser storage and can detect a Supabase session in the redirect URL.
- Native token auto-refresh is active only while the app is foregrounded.
- Web token auto-refresh remains enabled through the Supabase client.
- Logout calls `supabase.auth.signOut()`, clears the current app user, and returns to the auth screen.

## How domain restriction works

The allowed domain is normalized once in `src/config/domain.js`:

```js
EXPO_PUBLIC_ALLOWED_DOMAIN || 'hbplus.fit'
```

The configured value is converted to lowercase. Email validation converts the email to lowercase and trims surrounding whitespace, then requires it to end with exactly `@<allowed-domain>`.

Examples for the default `hbplus.fit` domain:

| Email | Result |
| --- | --- |
| `person@hbplus.fit` | Allowed |
| `Person@HBPLUS.FIT` | Allowed |
| `person@evilhbplus.fit` | Rejected |
| `person@hbplus.fit.evil.com` | Rejected |
| `person@gmail.com` | Rejected |
| `@hbplus.fit` | Supabase will reject this malformed address |

### First guard: form validation

`AuthScreen.js` prevents registration or login submission when `isAllowedEmail` is false. It shows a `Use your @hbplus.fit email.` field error.

### Second guard: authentication methods

`loginWithEmail` and `registerWithEmail` both call `isAllowedEmail` again before Supabase is contacted.

For Google sign-in, the app sends `hd=hbplus.fit` as a Google hosted-domain hint. This hint improves account selection but is **not a security guarantee**: Google, provider behavior, or OAuth configuration can still return a different address. The session gate below remains mandatory.

### Third guard: session gate

Every Supabase auth-state event passes through `handleSession` in `AuthContext.js`.

The session is accepted only when all three conditions are true:

1. A Supabase session and user exist.
2. `email_confirmed_at` is present.
3. `isAllowedEmail(user.email)` is true.

If the domain is wrong:

1. The app sets `DOMAIN_ERROR`.
2. It clears `user`.
3. It calls `supabase.auth.signOut()`.
4. The dashboard is not rendered.

If the email is unconfirmed, the app clears `user` and signs out without granting dashboard access.

### Fourth guard: database trigger

The recommended `auth.users` trigger rejects account creation for an email outside the allowed domain. This is important because a disallowed request can fail before or during provider authentication even if app validation is bypassed.

OAuth provider-side restrictions are useful for UX, but the database trigger and app session gate are the authoritative application controls.

### Database authorization

Domain checking determines whether a user can become an authenticated app user. Supabase RLS should determine what that authenticated user can read or modify.

The app fetches `profiles.role` after session validation. RLS policies must not rely only on a client-supplied role. For admin-only data, verify authorization in RLS or server-side functions and return only the minimum role needed by the UI.

## Error handling

Common Supabase codes are mapped to user-friendly messages:

| Supabase code or condition | UI behavior |
| --- | --- |
| `invalid_credentials` | Incorrect email or password |
| `email_not_confirmed` | Verification reminder |
| `user_already_exists` | Existing-account prompt |
| `weak_password` | Password-length guidance |
| Rate-limit codes | Short retry message |
| Database trigger/domain rejection | Official-domain access message |
| Network failure | Connection error |

Domain and confirmation errors are also surfaced as the `authError` value by `AuthContext`.

## Troubleshooting

### `EXPO_PUBLIC_ALLOWED_DOMAIN` is not taking effect

Stop Expo, update `.env`, and restart it. If running web or using an existing shell, also reload the app or use a new Expo process.

### Supabase environment variables are missing

Confirm both variables are set before starting Expo. The app creates the Supabase client with them and cannot authenticate without valid values.

### Google redirect is rejected

Check all of these allow lists:

- Supabase **Authentication > URL Configuration > Redirect URLs**
- Google OAuth authorized redirect URIs
- The exact web origin or native redirect URI used by the app

The web origin must include the correct protocol and port. Native Expo URI schemes vary by build and environment.

### Verification email is not changing the session

Open the email link in a redirect location allowed by Supabase. Confirm email verification is enabled and that the `emailRedirectTo` URL is correct. The app requires `email_confirmed_at` and rejects unconfirmed sessions.

### User exists but dashboard access is denied

Confirm:

- The account email ends in `@<EXPO_PUBLIC_ALLOWED_DOMAIN>`.
- `email_confirmed_at` is set.
- The database trigger uses the same domain.
- A valid Supabase session is restored.

### Profile role remains `User`

The app defaults to `user` when `profiles` has no matching role row or is inaccessible. Verify the profile row exists and that RLS permits the authenticated user to read it.

## Production notes

- Use HTTPS redirect URLs in production.
- Keep Supabase URL and public/publishable key in environment variables; never add the service-role key to the app bundle.
- Restrict OAuth origins and redirect URLs to the deployed app domains.
- Keep the app session gate, database trigger, and RLS policies aligned.
- Configure a real `profiles` table and admin role assignment process before granting privileged access.
- Restart and rebuild after changing public Expo environment variables.
